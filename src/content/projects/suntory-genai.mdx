## Overview

Built and shipped at **Beam Suntory** (a global beverages company),
where I've been AI Engineer since September 2025. The product is an
internal GenAI assistant for employees, sitting on top of enterprise
knowledge sources with multi-provider LLM routing, an evaluation harness,
and full request observability.

Specifics about the internal tool are sanitized — see the disclaimer at
the bottom. This case study covers architectural patterns and the
engineering work I owned, not the product itself.

## Problem framing

Large beverages companies sit on years of internal documentation,
dashboards, and process knowledge fragmented across many systems.
Employees waste hours per week locating answers that already exist. The
mandate I was given: build a conversational interface over this corpus
that meets enterprise standards for security, latency, observability, and
cost.

## Architecture

Standard RAG-with-routing topology, generic enough to share:

```
User query
  └─> Auth layer (SSO)
       └─> Query router (intent classification → specialized pipeline)
            └─> Retrieval (embedding search + keyword fallback + rerank)
                 └─> Context assembly with citation metadata
                      └─> LLM call (with provider failover)
                           └─> Post-processing (citation injection,
                               PII scrub, response validation)
                                └─> Observability sink + response
```

## Key decisions

### RAG over fine-tuning

Domain knowledge changes weekly — fine-tuning would have meant rebuilding
the model on every refresh. Retrieval keeps the model frozen and the index
mutable, which is the right axis to vary for a knowledge product. The
tradeoff is more compute per query and a more complex retrieval pipeline,
which we paid for with the observability investment.

### Multi-LLM routing from day one

Most prototypes start with one provider. We didn't, because:
- **Failover**: provider outages are inevitable; degrading to a backup is
  better than going dark
- **Cost shaping**: simple queries route to a cheaper tier, complex ones
  to a stronger model
- **Regulatory optionality**: different providers have different data
  residency stories; the routing layer is where that conversation
  happens

### Evaluation harness before optimization

We built a golden-dataset eval harness before we touched retrieval
parameters. Without it, every "improvement" was someone's vibe. With it,
the loop became: change one thing → measure on the harness → keep or
revert. This is the single most leveraged piece of infrastructure on the
project.
