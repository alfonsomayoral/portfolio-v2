## Overview

I joined **Beam Suntory** in September 2025 as an AI Engineer inside
the AI software team. My role spans the full lifecycle of enterprise
GenAI solutions: spotting business use cases worth building, designing
the architecture, implementing the end-to-end system on Azure with
security controls appropriate for an enterprise environment, and
iterating with stakeholders until the solution becomes part of a
team&apos;s daily workflow.

This case study describes the engineering patterns and the role. It
does not name the products, departments, customers, or absolute
metrics — that information is covered by the NDA. The architectural
choices and lessons are publicly shareable.

## My role

- **Designing solutions**: General-purpose agents, Model Context
  Protocol (MCP) tools, Azure use cases with a strong data-platform
  focus. Each solution targets a specific business workflow that a
  department already does manually.
- **End-to-end ownership**: From requirements gathering with the
  business stakeholder to deployment, observability, and handover.
- **Cloud architecture**: Building secure enterprise-grade
  architectures on Azure — auth, data residency, network isolation,
  audit logs, cost monitoring.
- **Fast iteration**: Ship a working prototype, get the business team
  using it, iterate in short cycles with real users instead of long
  upfront specs.

## Tech stack

- **LLM providers**: OpenAI (direct) and Azure OpenAI through Azure
  AI Foundry
- **Frameworks**: LangChain for orchestration on some workloads; the
  OpenAI **Agents SDK** for tool-using agent flows
- **Retrieval**: Azure AI Search (hybrid dense + keyword), OpenAI
  Vector Store for prototype workloads
- **Tool integration**: Model Context Protocol (MCP) for exposing
  internal tools to agents
- **Cloud**: Azure (primary) with some workloads touching GCP
- **Languages**: Python end-to-end

## Patterns I&apos;ve repeated across use cases

### Agents as the default interface

Instead of one monolithic chat app, each solution is a focused agent
with a specific scope, a curated toolset, and a clear handoff to a
human. The Agents SDK pattern (instructions + tools + guardrails)
ships faster than custom orchestration and survives provider upgrades
better.

### MCP for internal tool exposure

When the agent needs to read or write into an internal system, MCP is
the standard. It lets the same tool definition work across providers,
keeps tool definitions version-controlled, and makes the surface area
the security team has to review explicit.

### Hybrid retrieval over pure vector search

Azure AI Search&apos;s hybrid mode (dense + sparse + reranking) beats
pure embedding search on enterprise content, especially documents
with structured headers, codes, and proper nouns. The eval numbers
that justified this are NDA, but the qualitative finding is widely
reproducible.

### Iteration with the business, not for the business

The fastest path from "we have an idea" to "we use this every day"
is to put a rough version in front of the real user within one or two
weeks. Long specs miss the way the actual workflow differs from how
it is described in meetings.

## Scale and impact (sanitized)

I have led **5+ distinct use cases** across the company. Several have
moved from prototype to "the default tool that team reaches for"
within months — replacing manual processes that previously involved
spreadsheets, internal portals, and email chains. Specific absolute
metrics are NDA.

## What this year has taught me

- How to operate in an **enterprise environment**: security review,
  procurement, data-classification handling, change management
- How to **recognize a real business use case** versus a demo:
  workflows that are repeated weekly by multiple people are gold;
  one-off curiosity is not
- How to assemble **end-to-end secure cloud architectures** on Azure
  rather than just calling APIs from a notebook
- How to **iterate fast** under constraints that startups do not
  have — and to ship anyway

## What I&apos;d do differently

I started with LangChain on workloads where the OpenAI Agents SDK
(once it landed) would have been the better default. The agent
abstraction maps more cleanly to enterprise use cases, where each
solution is one focused capability and not a generic chatbot. I have
ported some of the early work and would now reach for Agents SDK
first by default.

## Why this role for an AI engineer

A non-tech Fortune 500 turns out to be a strong first job for an AI
engineer. The bar for adoption is not technical novelty, it is
"does this become the thing the user reaches for". You learn what AI
costs to operate, what enterprise procurement actually looks like,
how to talk to a non-technical stakeholder about what the model can
and cannot do. None of these are taught in startup blog posts.
